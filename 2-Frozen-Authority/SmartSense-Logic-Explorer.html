M3 Owner account creation & pairing

P0DEFINEDBothRelease 1: Foundation, Security & Ownership

Verified-email account identity. First successful claimant of a VIN becomes its Primary Owner; invited Authorized Users receive VIN-scoped access. One SmartSense account may be Primary Owner of multiple RVs and may also be an Authorized User on additional RVs; access and role are evaluated per VIN. Gateway claim requires local BLE to the Current Gateway, its manufactured pairing code, Gateway LTE, and cloud confirmation of claimable VIN/current Gateway. Direct TPMS claim uses verified account + VIN + local BLE presence proof of the factory sensor set; OD-009 defines the remaining exact criterion. No product-defined Authorized User cap.

Confirmed requirements (Spec v0.8)
  • Retail account identity uses verified email plus authentication; names are not required in current scope.
  • First successful claimant becomes Primary Owner for that VIN. Additional Authorized Users join by verified-email invitation; no current product-defined Authorized User cap exists. One account may be Primary Owner of multiple VINs and Authorized User on additional VINs, with role/access evaluated independently for each VIN.
  • For Gateway Product Mode, the pairing code is a Gateway-manufactured credential, printed on the device label and included in Gateway data reported to cloud. It is not a VIN credential.
  • Gateway-mode claim requires local BLE communication with the currently registered/current Gateway, the code from that Gateway, the Gateway itself online through LTE, and cloud confirmation that the VIN is claimable and the communicating Gateway is the Current registered Gateway.
  • Phone-only cloud connectivity is not a substitute for Gateway LTE; without Gateway LTE, Gateway-mode owner claim/activation cannot complete in current scope.
  • For Direct TPMS, no Gateway pairing code is used. Claim requires verified account + VIN + cloud confirmation that the VIN is claimable + local BLE presence verification of the VIN's factory-registered TPMS sensor set.
  • OD-009 remains open only for the exact Direct TPMS sensor-count/timing/presence criterion; the architecture itself is approved.
  • Authenticated email change requires new-email verification before effective and prior-email security notice where possible. Lost-access recovery uses controlled/audited SmartSense support/admin recovery; VIN + Gateway code alone is insufficient.
Process flow

Gateway claim: Verified account → VIN → Cloud confirms Product Mode=GATEWAY and claimable state → App establishes local BLE with Current Gateway → User/app presents that Gateway's manufactured pairing code → Gateway itself confirms LTE/cloud connectivity → Cloud confirms communicating Gateway is Current for VIN → Claim succeeds → user becomes Primary Owner. Direct claim: Verified account → VIN → Cloud confirms Product Mode=DIRECT_TPMS and claimable state → App locally verifies BLE presence of VIN's factory sensor set according to OD-009 criterion → Claim succeeds → user becomes Primary Owner. Multi-RV relationship rule: each VIN is claimed/released independently. Claiming or accessing one RV does not broaden access to any other VIN on the same user account.

M4 Gateway replacement on a vehicle

P0DEFINEDGateway / location-capable onlyRelease 1: Foundation, Security & Ownership

Gateway replacement is a controlled transaction (Started / Setup In Progress / Ready for Cutover / Complete, with Aborted). Old Gateway remains Current until atomic successful cutover; replacement must complete required configuration and TPMS pairing first.

Confirmed requirements (Spec v0.8)
  • Replacement is modeled as a separate Gateway Replacement Transaction/Job rather than changing the old Gateway association at the start.
  • Transaction states include Started / Setup In Progress / Ready for Cutover / Complete, with an Aborted path. Exact technical state names may be implementation-specific if these semantics are preserved.
  • The old Gateway remains the Current association until successful cutover.
  • The replacement Gateway is reserved/pending and may not become Current until required configuration and all required TPMS pairing are complete.
  • Mid-process failure may be resumed or aborted without losing the old Current Gateway relationship.
  • Cutover is atomic from the product perspective: new Gateway becomes Current; old Gateway becomes Replaced/Removed From Service; VIN history remains continuous.
  • Delayed telemetry from the replaced Gateway follows the controlled buffered/backfill/timestamp rules and cannot silently overwrite newer current state.
Process flow

Start replacement job → reserve eligible replacement Gateway → deliver/apply required configuration → pair all required Model TPMS positions → mark Ready for Cutover → atomic Current-Gateway switch → old Gateway becomes Replaced/Removed → retain VIN/device history. Abort at any pre-cutover point leaves old Gateway Current.
